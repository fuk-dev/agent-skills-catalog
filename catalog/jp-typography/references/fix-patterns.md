# 修正パターン

## 手法の選び方

| 症状 | 手法 | 理由 |
|---|---|---|
| **行頭に助詞が落ちる／最終行が孤立** | **`word-break: auto-phrase`** | **まずこれ。文節境界で折るので大半が消える。文言もマークアップも変えない** |
| **↑を iPhone / Firefox でも効かせたい** | **BudouX ＋ `keep-all`（`0.4`）** | auto-phrase は Chromium 限定。**iOS Safari は最新版でも未対応** |
| **行末に助詞が残る（カード本文）** | **「。」「、」に `"\n"` ＋ `WrapText`** | auto-phrase では消えない。文節境界＝助詞の直後だから |
| 行数・改行位置を決めたい | データに `"\n"` ＋ `WrapText` | 唯一確実。幅が変わっても崩れない |
| 特定の語を絶対に割りたくない | `whitespace-nowrap` | 語が行幅より短いことを**測ってから**使う |
| 中黒でつないだ一語 | WORD JOINER `U+2060` | マークアップ不要。データだけで完結する |
| 狭い端末でも行数を保証 | `.jp-fixed-lines` | 字送りを詰めて 1 行の字数を保つ |
| 和文中の半角スペース | ソースを1行に連結 | 原因は要素内のソース改行 |
| カード本文が細すぎる | `p-6 sm:p-8` / 多列は `lg` 以降 | そもそも幅が足りていない |

**使ってはいけない**: `text-wrap: balance`（行長を揃えるだけで改行位置は制御できず、語中で割れる）

---

## 0. `word-break: auto-phrase` — 最初に打つ手

文節境界を優先して折り返す。**個別対応に入る前に必ずこれを試し、再走査する。**

```css
p, li, dd, dt, figcaption { word-break: auto-phrase; }
```

これで直る症状:

```
NG  細部の仕上がり          NG  …窓口をひとつに。分離発注
    まで妥協しません。              の手間を省きます。

OK  細部の仕上がりまで      OK  …窓口をひとつに。
    妥協しません。                  分離発注の手間を省きます。
```

実測値は `SKILL.md` の表を参照（行頭助詞 414px で 24→5、最終行4字以下 414px で 9→0）。

**残る典型パターン**（auto-phrase が別文節として扱う複合辞・補助動詞）:

```
…製品・グレードに / より保証内容が…
…工事内容に       / よって異なります。
…災害（地震等）   / による損傷
…未来に責任を     / もち続けます。
…スピード感を     / もってお応えする。
```

数が少ないので、該当語を `.nb`（`white-space: nowrap`）で包む:

```astro
<span class="nb">グレードにより</span>
```

**限界**
- **Chrome/Edge 119+ のみ。iOS Safari は最新版でも未対応**（caniuse 実測 2026-08-12:
  iOS Safari 3.2〜26.5 すべて ❌ / Firefox 2〜156 ❌ / デスクトップ Safari は TP のみ）。
  無視されるだけで壊れはしないが、**iPhone では効果ゼロ**。和文サイトでモバイル比率が高いなら、
  「auto-phrase で N 件→0 件」という報告は**訪問者の一部にしか当てはまらない**。
  → 全ブラウザで揃えるなら次の **0.4 BudouX** を使う。
- `keep-all` と混同しない。auto-phrase は幅が足りなければ従来どおり折る。

## 0.4 BudouX — auto-phrase を全ブラウザに広げる

`word-break: auto-phrase` の**ブラウザ非依存版**。Google の BudouX で文節境界を
**ビルド時に**判定し、その位置に `<wbr>` を置く。Chromium 以外でも文節で折れるようになる。

```bash
npm i -D budoux   # devDependency。ビルド時のみ使う
```

### 使い方（Astro・ビルド時）

**`translateHTMLString()` を使ってはいけない。** 区切りに **ZWSP (U+200B)** を挿入するため、
コピペ・`Ctrl+F`・構造化データに**不可視文字が混入する**（#3 の U+2060 混入と同じ事故）。
`parse()` でチャンクを取り出し、**自分で `<wbr>` に変換する**。

```ts
// src/lib/budoux.ts
import { loadDefaultJapaneseParser } from 'budoux';
const parser = loadDefaultJapaneseParser();

const esc = (s: string) =>
  s.replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;');

/** 和文を文節境界で <wbr> 区切りにする。戻り値は set:html で出す */
export const phrase = (text: string) =>
  parser.parse(text).map(esc).join('<wbr>');
```

```astro
---
import { phrase } from '../lib/budoux';
const { text } = Astro.props;
---
<span class="jp-phrase" set:html={phrase(text)} />
```

```css
.jp-phrase {
  word-break: keep-all;        /* CJK の任意位置での改行を禁止 */
  overflow-wrap: anywhere;     /* 1 文節が枠より長いときの安全弁。必須 */
}
```

この 3 点セットで初めて機能する。`<wbr>` は**改行可能地点を増やすだけ**で、
禁止はしない。`keep-all` が無いと Safari は従来どおりどこでも折る。

### 実測（2026-08-12 / budoux 最新・Node 24）

```
IN   売却・賃貸に向けた内外装の整えを、確かな品質で。細部の仕上がりまで妥協しません。
OUT  売却・<wbr>賃貸に<wbr>向けた<wbr>内外装の<wbr>整えを、<wbr>確かな<wbr>品質で。<wbr>細部の<wbr>仕上がりまで<wbr>妥協しません。
```

- 日本語モデル **20.5 KB**。**ビルド時のみ**なので `dist` への追加は 0 バイト
  （増えるのは `<wbr>` 5 バイト × 文節数の HTML のみ）。クライアント JS も 0。

### auto-phrase との関係（重要）

**併用できない。** `keep-all` と `auto-phrase` は**同じ `word-break` プロパティの値**なので、
`.jp-phrase` の `keep-all` が親の `auto-phrase` を**上書きする**。両立ではなく**置換**。

| | 適用範囲 | 効くブラウザ |
|---|---|---|
| `auto-phrase` | 全体（CSS 1 行） | Chromium のみ |
| BudouX + `keep-all` | `.jp-phrase` で包んだ箇所 | **全ブラウザ** |

実務では **両方置く**のが正解。BudouX を適用した箇所はそちらが勝ち、
包み忘れた箇所は auto-phrase が Chromium で拾う、という二段構えになる。

### 実測で判明した弱点 — BudouX でも解決しないもの

**① 複合辞は auto-phrase と同じように割れる**（8 件中 7 件）

```
NG  「により」  → ["資産価値に","より","判断します。"]
NG  「によって」→ ["資産価値に","よって","判断します。"]
NG  「による」  → ["資産価値に","よる","判断します。"]
NG  「をもって」→ ["資産価値を","もって","判断します。"]
NG  「について」→ ["資産価値に","ついて","判断します。"]
NG  「として」  → ["資産価値と","して","判断します。"]
NG  「をはじめ」→ ["資産価値を","はじめ判断します。"]
OK  「にのみ」  → ["資産価値にのみ","判断します。"]
```

**ただし BudouX なら個別対応せずに一括で潰せる**（auto-phrase にはできない）。
`.jp-phrase` は `keep-all` なので、**`<wbr>` を置かなければそこは割れない**。
つまり「境界を作らせない」ことが直接の対策になる。パース結果を結合するだけでよい:

```js
// scripts/jp-compounds.mjs — 複合辞のリストは 1 ファイルに集約する（複数箇所に書くとズレる）
export const COMPOUNDS = [
  'という', 'といった', 'として', 'とともに', 'にとって', 'について', 'により', 'によって',
  'による', 'において', 'における', 'に対して', 'に関して', 'をもって', 'をはじめ',
  'のために', 'にわたって', 'に沿って', 'に応じて', 'を通じて', 'を通して', 'にあたって',
  'に基づく', 'に基づき', 'に限り', 'ならびに', 'とおり', 'ことで', 'ことが', 'ものの',
  'ています', 'ていく', 'てくる', 'ておく', 'てきた', 'ていた', 'ている',
  'いただく', 'いただき', 'いただけ', 'ください', 'できます', 'できる',
  'もち続ける', 'し続ける', 'つづける',
];
export function spansCompound(joined, at) {
  for (const c of COMPOUNDS) {
    const idx = joined.indexOf(c, Math.max(0, at - c.length + 1));
    if (idx !== -1 && idx < at && idx + c.length > at) return c;
  }
  return null;
}
```

```js
// 複合辞をまたぐ境界を潰す
function mergeCompounds(chunks) {
  const out = [];
  for (const c of chunks) {
    const prev = out[out.length - 1];
    if (prev && spansCompound(prev + c, prev.length)) { out[out.length - 1] = prev + c; continue; }
    out.push(c);
  }
  return out;
}
const chunks = mergeCompounds(parser.parse(text));
```

実案件（YUMA PLANNING 19ページ）では**24箇所 / 12種 → 0箇所**。
データも文言も触らず、**今後書く文章にも自動で効く**。`.nb` を1箇所ずつ足す運用は不要になる。

> **`<wbr>` が 0 個になっても `.jp-phrase` は必ず付けること。**
> 「保証について」のように境界が 1 つだけで、それが複合辞ゆえに潰れると `<wbr>` が 0 個になる。
> ここで「変化なし」と判定して class を付けないと、その要素は auto-phrase 任せに戻り、
> **Chromium が「保証に／ついて」と割る**。実案件でこれを踏んで、対象要素が 248 → 912 に増えた。

なお **auto-phrase 側はこの手が使えない**（ブラウザ内部の判定なので介入できない）。
BudouX を入れていない要素に残る複合辞は、従来どおり `.nb` で包むしかない。

**② 中黒の直後に改行地点を作ってしまう**（新規発見・要注意）

```
売却・<wbr>賃貸に…        ← 中黒の直後で割れるようになる
オンライン・<wbr>対面の…   ← 同上
設計・開発・運用まで<wbr>…  ← こちらは割れない（判定が不安定）
```

`keep-all` 単体なら中黒でも折れないのに、**BudouX が `<wbr>` を置くことで割れるようになる**。
つまり BudouX は「オンライン・／対面」という既知の症状を**自分で作り出す**。
→ 対処は従来どおり **WORD JOINER (U+2060) を中黒の直後に置く**（`4.` 参照）。
**BudouX 導入後は中黒を含む語を必ず再走査すること。**

**③ 空白入りの欧文固有名詞は守られない**

```
["YUMA PLANNING が","対応します。"]   ← 1 チャンクだが…
```

`keep-all` が禁じるのは **CJK 間の改行だけ**で、**半角スペースでは従来どおり折れる**。
→ `.nb-en`（`white-space: nowrap`）は引き続き必要。

**④ 行末に助詞が残る症状は消えない（むしろ広がる）**

文節境界＝助詞の直後なので、`0.5 WrapText` と**必ずセットで導入する**。
BudouX 単体で入れると、Chromium にしか出ていなかったこの症状を
**iOS Safari にも広げることになる**。

### 適用してはいけない場所

`<wbr>` はタグなので、**テキストとして扱われる経路に入れると壊れる**。

- JSON-LD（構造化データ）、`<title>`、`meta[name=description]`、OG、`alt`
- `llms.txt` / `llms-full.txt`、サイトマップ、RSS

**データ（`*.ts` の文字列）は素のまま保ち、表示直前にだけ `phrase()` を通す。**
`WrapText` と同じ原則。導入後は必ずビルド後の全 HTML を走査し、
**構造化データへの `<wbr>` 混入 0 件**を確認する（ビルド後の HTML をテキスト検索すればよい）。

## 1. WrapText — データは素のテキストのまま、改行位置だけ指定する

データ（`services.ts` `faq.ts` 等）の文字列は、構造化データ・alt・meta でも使う。
`<br>` を直接書くとタグが混ざる。**改行位置は `"\n"` で表し、表示時にだけ `<br>` へ変換する。**

### コンポーネント（Astro）

```astro
---
/** データ側の "\n" を改行として描画する。
 *  until は改行を有効にする上限のブレークポイント。
 *  - "md"  (既定): 768px 未満で有効
 *  - "lg"        : 1024px 未満で有効（多列グリッドのカードはこちら）
 *  - "none"      : 常に改行（幅が戻らない細いカード）
 */
interface Props {
  text: string;
  until?: "md" | "lg" | "none";
}
const { text, until = "md" } = Astro.props;
const lines = text.split("\n");
---

{
  lines.map((line, i) => (
    <Fragment>
      {line}
      {i < lines.length - 1 &&
        (until === "none" ? <br /> : until === "lg" ? <br class="lg:hidden" /> : <br class="md:hidden" />)}
    </Fragment>
  ))
}
```

### データ側

```ts
// 改行位置は "\n"。文言そのものは変えない。
summary: "UI/UXと品質にこだわり、\nWebアプリ・サイトの画面開発を担当。",
```

### 構造化データからは必ず除去する

```ts
// FAQPage / Service など、同じ文字列をスキーマに出すところ
acceptedAnswer: { "@type": "Answer", text: f.a.replace(/\n/g, "") },
description: description.replace(/[\n⁠]/g, ""),   // WORD JOINER も除く
```

**確認方法**: ビルド後の HTML で `grep -o '"text":"[^"]*"'` して、改行記号が出ていないこと。

### `until` の決め方

| 置き場所 | until | 理由 |
|---|---|---|
| 本文・リード文（全幅） | `md` | md 以上は幅に余裕があり自然折り返しで整う |
| 2列グリッドのカード | `lg` | 768〜1023px で 1 枚あたりがモバイルより狭くなる |
| 3列グリッドのカード | `none` | lg で 3 列になると 245px 程度まで下がり、戻らない |

**判断の根拠は実測が理想**だが、実描画を測れない環境では上表を既定として使う。

## 2. `.jp-fixed-lines` — 狭い端末で行数を保証する

`<br>` を入れても、**決め打ちしたセグメント自体が狭い端末でさらに折り返す**ため行数は保証できない。
画面幅に応じて字送りをわずかに詰め、1 行あたりの字数を保つ。

```css
/* Tailwind の md: は min-width:48rem。max-width:767px と書くと、
   dPR 1.25 などで論理幅が 767.2px になる端末で「どちらの条件にも入らない穴」が開き、
   md:hidden の br だけが効いた状態になる。md: のちょうど裏返しで書くこと。 */
@media not all and (min-width: 48rem) {
  .jp-fixed-lines {
    /* 3.4vw: 最長行が 360px 幅の本文領域に収まる係数
       上限 0.875rem は text-sm、下限 0.72rem は 320px 端末の下支え */
    font-size: clamp(0.72rem, 3.4vw, 0.875rem);
  }
}
```

**保証範囲**: 360px 以上。320px（iPhone SE 第1世代相当）は行数が増えるが、
対応機種がほぼ存在しないため許容とする。

**係数の調整**: 最長セグメントの実測幅 ÷ 最小端末の本文幅 で決める。
実描画を測れない場合は、和文 1 文字の幅 ≒ font-size として見積もる。

## 3. `whitespace-nowrap` — 語を割らせない

英字を含む複合語、鍵括弧で囲んだ引用に使う。

```astro
現在は、<span class="whitespace-nowrap">生成AI</span>を事業に組み込む<span
  class="whitespace-nowrap">「AX（AI Transformation）」</span>のご支援に力を入れています。
```

**必ず先に測る。** 語が行幅より長いと横にはみ出す。

```
「AX（AI Transformation）」 = 193px、本文幅 367px → 安全
```

データ側の文字列に使いたい場合は、テンプレートで対象語を包むか、次の WORD JOINER を使う。

## 4. WORD JOINER (U+2060) — 中黒での改行を禁じる

幅ゼロ・不可視の改行禁止文字。**マークアップ不要でデータだけで完結する**のが利点。

```ts
// 「開発・」で行が切れて「ご提供します。」が次行に落ちるのを防ぐ
description: "…システムとして開発・⁠ご提供します。…",
```

ソースでは不可視なので、**必ずコメントを添える**。

```ts
// ⁠ は WORD JOINER（幅ゼロ・不可視の改行禁止文字）。中黒での改行を禁じる。
{ t: "ヒアリング", d: "現状の課題と目標を伺います。オンライン・⁠対面どちらも可能です。" },
```

**注意**
- 1 箇所の改行を禁じるだけ。語全体を不可分にしたいなら `whitespace-nowrap` を使う
  （全文字間に入れるのは非現実的）。
- 構造化データからは `replace(/[\n⁠]/g, "")` で除去する。
- 行抽出スクリプトでも除去してから比較する（さもないと文字列比較がずれる）。

## 5. 和文中の半角スペースを消す

原因は**要素内のソース改行**。HTML の空白圧縮で半角スペース 1 個になる。

```astro
<!-- NG: 「開発会社です。␣Webシステムの…」と空きが出る -->
<p>
  イードライブは、2019年の設立以来、Webに特化して事業を続けてきた福岡の開発会社です。<br class="hidden xl:block" />
  Webシステムの開発と…
</p>

<!-- OK: 1行に連結する -->
<p>
  イードライブは、…福岡の開発会社です。<br class="hidden xl:block" />Webシステムの開発と…
</p>
```

**`<br class="hidden ...">` の前後は特に危険**: br が消える幅でだけ空きが出るため、
PC で見ている限り気づけない。

行が長くなるが、**和文は 1 文 1 行で書く**を原則にする。

## 6. レイアウト側の対処

改行の問題に見えて、**実は幅が足りていない**ことが多い。先にこちらを疑う。

### カード内側の余白

```
p-8（32px×2）: 375px 端末で本文 262px → 1行17字。語割れが多発
p-6（24px×2）: 375px 端末で本文 294px
```

```astro
<div class="p-6 sm:p-8">
```

### 多列グリッドは `lg` 以降

```
md:grid-cols-4  → 768px で 1枚あたり 101px（説明文が2〜6字で刻まれる）
md:grid-cols-3  → 768px で 1枚あたり 約200px
```

```astro
<!-- NG -->
<ol class="grid gap-6 md:grid-cols-4">
<!-- OK -->
<ol class="grid gap-6 sm:grid-cols-2 lg:grid-cols-4">
```

### 均等幅グリッドに項目リストを流し込まない

和文の項目名は 4〜6 字が多く、均等幅にすると列間に 80〜110px の空きができる。

```astro
<!-- NG: grid-cols-2 が親幅いっぱいに広がる -->
<ul class="grid grid-cols-2 gap-2">
<!-- OK: 列幅を内容に合わせ、リンク群を1つの塊にする -->
<ul class="grid w-fit grid-cols-2 gap-x-10 gap-y-2">
```

## 7. 収まらないときの扱い

物理的に入らない指定を受けたら、**黙って諦めず、幅と文字数の見積もりを添えて説明する**。

```
使える幅                                   318px
「という段階からでも、課題の整理からご一緒します。」  351px
→ 33px 足りない。余白を p-6→p-4 にしても 16px しか稼げず届かない。
```

そのうえで選択肢を出す。

1. 現状の行数のまま（文言を変えない）
2. 文言を縮める → **具体案を提示してユーザーに選んでもらう**

```
変更前: という段階からでも、課題の整理からご一緒します。  351px
変更案: という段階から、課題の整理をご一緒します。        306px
```

**ユーザーが決めた文言を断りなく削らない。** 意味の芯に関わる語（例:「でも」＝受け入れの含み）は、
落とす影響も併せて説明してから判断を仰ぐ。
