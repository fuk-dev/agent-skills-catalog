# 生成時に守る規約

**修正より生成時に守るほうが安い。** 新規構築時はここを先に読む。
実案件では、これを守っていれば 25 往復の指摘のうち 9 割が発生しなかった。

---

## A. 割ってはいけない語

行をまたぐと読めなくなる、または誤読される語。

| 種類 | 例 | 手法 |
|---|---|---|
| 英字を含む複合語 | 生成AI、AI活用、Webシステム、DXコンサル | `whitespace-nowrap` |
| 中黒でつないだ一語 | 設計・開発、オンライン・対面、企画・制作 | WORD JOINER `U+2060` |
| 鍵括弧で囲んだ引用 | 「何から始めればよいか分からない」 | `whitespace-nowrap` |
| 括弧付きの用語 | AX（AI Transformation） | `whitespace-nowrap` |

### 対象外 — 列挙の中黒

`A・B・C` のような**列挙の中黒は、行末に置くのが正しい組版**。次行の頭に落とすほうが誤り。

```
OK:  Webシステム開発・AIシステム開発・      ← 中黒が行末
     DXコンサルティング・Webマーケティング

NG:  Webシステム開発・AIシステム開発
     ・DXコンサルティング…                  ← 中黒が行頭
```

**「一語」か「列挙」かは意味で判断する。** 機械的には区別できない。
- 「設計・開発」= 一続きの工程 → 一語。割らない
- 「Webシステム開発・AIシステム開発・DXコンサル」= 4つのサービス → 列挙。割ってよい

## B. 改行と行数

1. **和文テキストを要素内で改行しない。**
   ソースの改行は半角スペースになる。1 文が長くても 1 行に書く。
   `<br class="hidden ...">` の前後は特に危険（br が消える幅でだけ空きが出る）。

2. **改行位置はデータ側で `"\n"` として持つ。**
   データに `<br>` を書くと構造化データ・alt・meta にタグが混ざる。
   初期構成に `WrapText` 相当を含めること。**後付けは 3 回目の同種指摘で作ることになる。**

3. **`text-wrap: balance` を改行位置の制御に使わない。**
   行長を揃えるだけ。実測で 375px の見出しが「システム開」/「発・リース」と**語中で割れた**。

4. **`word-break: auto-phrase` を初期構成に必ず入れる。**

   ```css
   p, li, dd, dt, figcaption { word-break: auto-phrase; }
   line-break: strict;   /* 長音符・小書き仮名の行頭落ちを防ぐ。別問題なので併用する */
   ```

   文節境界で折るため「行頭に助詞が落ちる」「最終行が孤立」がまとめて減る。
   実測で行頭助詞 414px 24件→5件、最終行4字以下 414px 9件→0件（`SKILL.md` の表）。
   **1行入れるだけで効くので、入れ忘れると同じ指摘を何度も受ける。**

   ただし **Chromium 限定**。「〜により」「〜によって」などの複合辞は残るので、
   その数件は `.nb`（nowrap）で包む。

4.5. **一般公開の和文サイトなら BudouX も初期構成に入れる。**

   `auto-phrase` は **iOS Safari が最新版でも未対応**（caniuse 実測 2026-08-12:
   iOS Safari 3.2〜26.5 / Firefox 2〜156 がいずれも未対応）。
   和文サイトはモバイル比率が高く、その大半が iOS Safari なので、
   **4 だけでは「訪問者の一部にしか効いていない」状態になる。**

   ```bash
   npm i -D budoux
   ```
   ```ts
   export const phrase = (t: string) => parser.parse(t).map(esc).join('<wbr>');
   ```
   ```css
   .jp-phrase { word-break: keep-all; overflow-wrap: anywhere; }
   ```

   - **ビルド時のみ。** モデル 20.5KB もクライアント JS も `dist` に載らない。
   - **`translateHTMLString()` は使わない**（ZWSP U+200B が混入する）。`parse()` + 自前 `<wbr>`。
   - **`WrapText` とセットで入れる。** 単体だと「行末に助詞が残る」を iOS にも広げる。
   - **中黒の直後に `<wbr>` が入る**ため、「オンライン・／対面」を自分で作り出す。
     中黒を含む語は WORD JOINER で個別に潰す（A 章参照）。
   - `<wbr>` を構造化データ・`title`・`meta`・`alt`・`llms.txt` に入れない。
   - 詳細は `fix-patterns.md` の `0.4`。

5. **`<br>` だけでは「絶対に N 行」を保証できない。**
   決め打ちしたセグメント自体が狭い端末で折り返す。`.jp-fixed-lines` を併用し、
   **360px 以上で保証**する（320px は対象外と割り切る）。

6. **本文サイズは `text-sm md:text-base` を既定にする。**
   モバイルで `text-base`(16px) だと 1 行 21 字しか入らず、折り返しの事故が増える。

7. **Tailwind と連動する自作 CSS を `max-width: ○px` で書かない。**
   `md:` は `min-width: 48rem`。`max-width: 767px` と書くと、論理幅が 767.2px のような
   端数になる端末で**両方の条件から外れる穴**が開き、`md:hidden` の `<br>` だけが効く。
   `@media not all and (min-width: 48rem)` と裏返しで書く。

## C. レイアウト

8. **多列化は `lg` 以降。**
   `md:grid-cols-3/4` は 768px で 1 枚あたり 101〜200px になり、**モバイルより狭い**。
   `sm:grid-cols-2 lg:grid-cols-4` の形にする。

9. **カード内側の余白は `p-6 sm:p-8`。**
   モバイルで `p-8` は画面幅の 17% を余白に使う（375px 端末で本文が 262px しか残らない）。

10. **項目リストを均等幅グリッドに流し込まない。**
    和文の項目名は 4〜6 字が多く、均等幅だと列間に 80〜110px の空きができる。
    `w-fit` で内容幅に合わせる。

11. **背景の装飾タイポは幅基準（vw）だけで指定しない。**
    モバイルは縦長になり、同じ vw 係数でも縦の占有率が PC の 1/3 に落ちる。
    サイズを変えたら**端の切れ・重なり・字形の終端**まで確認する
    （A/X のようにベースラインで平らに終わる字形は、下端が画面を分断する水平線に見える）。

## D. 文章の書き方

12. **FAQ の回答は「1行目＝直接の答え」で書く。**

    ```
    Q. 相談だけでも対応してもらえますか？
       はい。                                    ← 1行目は答えだけ
       「何から始めればよいか分からない」
       という段階のご相談から承っています。
    ```

    - はい/いいえで答えられる質問 → 「はい。」で始める
    - 答えられない質問（「〜を教えてください」「どちらが良いですか」「どのような〜」）
      → **「はい。」は文法的に成立しない。** 1 文目を直接の答えとして独立させる

    見た目の統一だけでなく、AI 検索（LLMO）が答えを抜き出しやすい構造でもある。

13. **枠に入れる文は生成時に文字数上限を設ける。**
    目安: **カード本文 1 行 18 字・全 5 行**。
    後から縮めると承認の取り直しになる（実案件で 2 回発生）。

14. **同一カード群で常体の体言止めと敬体を混在させない。**
    「〜可。」と「〜します。」が並ぶと、片方だけ途切れて見える。

## E. 検証

15. **検証幅は 360 / 390 / 414 / 768 / 1024px。**
    モバイル 3 幅では足りない。**768 と 1024 を必ず入れる。**
    多列グリッドはブレークポイント直後に 1 枚あたりの幅が最小になるため、
    モバイルだけ見ても PC だけ見ても発見できない。

16. **入場アニメを止めてから測る。**
    `transform: translateY()` が残った状態だと位置が数十 px ずれ、誤った結論に至る。

17. **生成した文面・マークアップを出力後に自分で確認する。**
    観点は 3 つ。
    - 和文の間の半角スペース（**タグをまたぐケースも含めて**）— テキスト検索で確認できる
    - 語・鍵括弧が行をまたぐ箇所 — 実描画が必要。本スキルは A〜C の予防で潰す
    - 最終行が孤立している段落 — 同上

    実描画の計測は本スキルの範囲外。**予防（A〜C）を初期構成に入れることで、
    描画して測らなくても大半が発生しない状態にする**のが本スキルの方針。

## F. 進め方

18. **指摘が1件でも、その症状で全ページを走査してから一括で直す。**
    **最重要。** 実案件の最大の損失はこれ。症状の性質は最初の 1 件で分かるのだから、
    そこで走査すれば 25 往復が 3〜4 往復で済んだ。

19. **スクリーンショットが来たら、指示された箇所以外の欠陥も併せて洗い出す。**
    実案件では「はい。が無い」という指摘に対して「はい。」だけ足し、
    同じ画像に写っていた「生成」/「AI」の語割れを見落として 1 往復無駄にした。
